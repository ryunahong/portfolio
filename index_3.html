PM

타겟서비스 — 데이터 비전문가를 위한 셀프서브 타겟 빌더

마케터 → BDA 쿼리 요청 → 수동 등록으로 이어지던 레거시(CXM) 프로세스를, 빌더 UI만으로 조건 탐색부터 목록 추출까지 끝내는 셀프서브 플랫폼으로 전환

개요
사내 데이터 비전문가(PM, 마케터 등)가 SQL 지식 없이 타겟조건을 탐색·조합하고, 대상 목록을 추출·활용하는 타겟팅 플랫폼. 빌더 UI에서 선택한 필터가 SQL로 변환되는 구조
역할
  • 서비스 기획 (빌더 구조, 필터 체계, 활용 정책)
  • 필터 내부의 복잡한 쿼리 로직 기획 및 UI화
  • 레거시 플랫폼(CXM) 종료 및 타겟서비스 전환 로드맵 수립
배경
  • 운영 병목조건 쿼리화 요청 → BDA 쿼리 작성 → 사용자가 쿼리를 복사해 수동 등록. BDA 의존도가 높고 리드타임이 김
  • 데이터 탐색사내 DB·테이블·컬럼 경로를 사용자가 직접 파악해야 함
  • 휴먼 에러필터별 입력 가이드 부재 (예: 날짜 형식 yyyymmdd / yyyy-mm-dd 혼동)
  • 표현력단순 조건만 UI 제공, 조금만 복잡해도 쿼리 직접 입력 필요
  • 안정성Impala/Trino 혼용, 레거시 엔진 한계로 쿼리 타임아웃·실패 빈번
  • 업무 동선메시지 발송 등 실제 활용처와 어드민이 분리되어 맥락 단절
한 일
복잡한 쿼리 로직의 UI화
  • 상대기간: '최근 N일'로 설정, 실행 시점 기준 기간 자동 계산
  • epoch 변환: epoch 값을 날짜로 변환 후 조건 적용
  • 람다함수(ANY_MATCH): array 타입 데이터도 IN / NOT IN처럼 설정
  • 리타겟/디타겟: 이력 데이터 기반 포함·제외 설정
  • %LIKE% 부분 매칭, 정렬/랭크(상위 N명·N%) 필터링
쿼리 최적화·안전장치
  • 동일 테이블 조건 자동 병합 (이력성 테이블은 결과 왜곡 방지를 위해 분기 처리)
  • 파티션키 필수 설정, 테이블별 null 정책에 따른 null guard
  • 조건 설정·저장 시점마다 쿼리 플랜을 체크해 풀스캔 쿼리 사전 차단
활용 정확도·정책
  • 필터별 플레이스홀더·디스크립션, 데이터 타입에 맞는 UI 컴포넌트 제공
  • 설치 환경별·활용 목적별 약관 강제 적용 (기본 ON)
  • Trino 단일 엔진으로 표준화
플랫폼 구조
  • 메시지·오퍼 등 활용 플랫폼에 빌더를 임베드해 업무 동선 통합
  • 목록 추출·파일 다운로드(CSV/XLSX)·API, 추출 이력 관리
  • 실시간 타겟 판단용 데이터 배치 자동화(HBase 대체), 비트맵 기반 데이터 일원화로 추출-배치 간 모수 정합성 확보
결과
  • 현재 빌더 로직으로 기존 CXM 유즈케이스의 약 65% 처리 가능 확인 (2026.04 기준, LIKE 배포 시 확대)
  • CXM 어드민 종료 및 타겟서비스 통합 전환 진행 중

PM

AI 기반 타겟조건 탐색·추천 개발 중

자연어 입력을 표준화된 SQL 필터 단위(필터 + 연산자 + 값)로 매핑해 추천. AI가 SQL을 직접 생성하지 않고 검증된 필터만 추천하도록 설계

개요
빌더 사용자가 원하는 타겟을 자연어로 입력하면, 타겟서비스에 등록된 SQL 필터 중 적합한 것을 찾아 필터 + 연산자 + 값 단위의 타겟조건으로 추천하는 기능
역할
기능 기획 — 추천 정책, 사용자 플로우, 운영 구조 설계
배경
  • 카테고리 4,752개, SQL 필터 46,922개 규모로 계속 증가 → 사람이 검색해서 찾는 방식은 한계
  • CXM 종료 이후, 조건을 못 찾아 BDA에 다시 쿼리를 요청하는 상황을 줄여야 함
  • 표준화된 SQL 필터 사용을 최대화하고, 필터로 소화할 수 없는 케이스에만 raw SQL을 허용하는 활용 정책
한 일
AI가 SQL을 생성하지 않고, 검증된 필터를 추천
  • Text-to-SQL 대신 표준화·검증된 필터로 매핑해 존재하지 않는 테이블·컬럼 생성을 원천 차단
  • 빌더의 쿼리 최적화·null guard·약관 정책이 AI 추천 조건에도 그대로 적용
최종 결정은 사용자 (Human-in-the-loop)
  • AI는 후보만 제시하고 사용자가 확인 후 선택해 조합에 추가
  • 논리 연산, 약관, 정렬/랭크, 모수 제한은 기존 빌더에서 이어서 설정
불확실성에 따른 응답 정책
유사도 75% 이상 필터 존재추천 가능 조건으로 판단
75% 이상 후보 없음'추천 불가'로 응답 (억지로 매핑하지 않음)
후보가 여러 개모두 제공 (예: '30대' → 연나이·만나이·연령대)
값이 명확함값까지 채우되 수정 가능 (예: 거주지 = 서울시)
값이 불명확함필터만 추천, 값은 빈칸 (예: 가맹점 CID = { })
지속 개선이 가능한 운영 구조
  • 채팅 ID 단위 요청·응답 로깅 (Langfuse 연동)
  • '추천 불가' 키워드를 모아 신규 필터 우선순위에 반영하는 필터 확장 루프
  • 임베딩 갱신: 야간 배치 전체 재색인 + 변경 시 즉시 반영, 모델 교체에 대응하도록 임베딩 모델 비고정
  • 프롬프트 버전 관리·롤백, 지식베이스 검색 결과를 런타임에 주입하는 RAG 구조
단계별 범위
Phase 1싱글턴 추천, 로깅, 임베딩·프롬프트 관리
Phase 2멀티턴 세션, 만족도 피드백, 추천 조건 중 실제 선택 조건 로깅(추천 품질 지표화)
결과

개발 중 · 기대 효과

  • 조건 발견부터 활용까지의 탐색 시간 단축
  • BDA의 쿼리 대리 작성 리소스 감소
  • 추천 불가 로그 기반 필터 확대 → 빌더 효용 증대의 선순환
  • [출시 후: 추천 채택률 · 추천 불가율 · BDA 요청 건수 변화]
